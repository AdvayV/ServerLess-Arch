    How this follows the FaasCache paper

    Keep-alive cache (section 4): ready containers are like cached items. Reusing one is a cache hit; creating one is a cold start. Containers doing work are protected.

    Greedy-Dual priority (section 4.1): priority = access clock + invocation frequency × startup cost ÷ memory. When space is needed, remove the idle container with the lowest priority. The logical clock advances on removals; it is not elapsed time. Expensive-to-start, popular, smaller services tend to get higher priority.

    Comparison rules (section 4.2): LRU uses recency and LFU uses frequency. The fixed timer illustrates the timeout approach the paper replaces.

    Provisioning (section 5): changing the memory dropdown demonstrates the memory/performance tradeoff. The paper also sizes resources using reuse-distance curves and a dynamic controller; those are not implemented here.

    System components (section 6, figure 4): our request trace and Python container pool stand in for incoming requests and the OpenWhisk ContainerPool. FastAPI displays the simulation. We do not run OpenWhisk, Docker, or VM scaling.

    Experimental variation: the recent-demand rule lets older requests gradually lose influence, then weighs estimated reuse against startup cost and memory. It may help with changing demand, but these tiny traces cannot establish an improvement over FaasCache.

    About the college example and simulation

    The four services are timetable viewing (128 MiB), assignment submission (256 MiB), semester-report viewing (512 MiB), and fee payment (128 MiB). One ready copy of each needs 1,024 MiB.

    All activity and timings are illustrative Python simulation inputs. The demo enforces an idle-memory budget after requests finish; the paper constrains warm and running containers by physical server capacity. Here, working capacity is assumed sufficient, so requests never queue. We compare identical traces, including total startup delay rather than only counting cold starts.
